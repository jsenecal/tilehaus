# CLAUDE.md

Guidance for Claude Code (claude.ai/code) working in the Tilehaus repo.

## What this is

Tilehaus turns affordable ESP32-P4 LVGL touchscreens into Home Assistant control
panels. Two surfaces:

1. **Firmware** — native-LVGL C++ (`firmware/native/`, namespace `tilehaus`) driven
   by ESPHome YAML (`firmware/tilehaus.yaml` + `hardware/ui/fonts/bindings.yaml`).
2. **Web configurator** — a TypeScript browser page (`web/`) served by the device
   that edits a binary **DECK** document (the panel's tile layout).

Tilehaus is an independent sibling to
[EspControl](https://github.com/jtenniswood/espcontrol) — it reuses EspControl's
product concepts and visual language but shares no firmware code.

## Repo layout

- `firmware/` — ESPHome config + `native/` (C++ headers) + `assets/` (MDI TTF +
  glyph lists). `esphome: includes: [native]` pulls the headers into the build.
- `web/` — the configurator; `web/model/{deck,grid_layout}.ts` is the binary DECK
  codec + grid math (shared byte-for-byte with `firmware/native/deck_document.h`).
- `scripts/` — `build_deck_ui.js`, `build_icon_catalog.js`, `gen_deck_fixture.js`,
  `deck_cli.js` (panel CLI), `load_typescript_module.js`.
- `tests/{web,firmware}/` — deck-codec tests + native host tests.
- `docs/` — Zensical documentation site.

## Authored vs generated — never hand-edit generated files

- `firmware/native/deck_ui_asset.h` — generated by `npm run build` (gzipped web
  bundle). Git-ignored.
- `web/icon_catalog.ts` — generated by `npm run gen:icons` from
  `firmware/assets/icon_glyphs.yaml`.
- `tests/firmware/fixtures/*.bin` — generated by `npm run gen:fixtures`.

Edit the source (`web/*.ts`, `web/model/deck.ts`, `firmware/assets/*.yaml`), then
regenerate.

## Commands

- `npm run build` — bundle the web UI into `firmware/native/deck_ui_asset.h`.
- `npm run typecheck` / `test:web` / `test:firmware` / `gen:icons` / `gen:fixtures`.
- Firmware (ESPHome lives in its own venv, kept out of the repo's `.venv`):
  - one-time: `uv venv .venv-esphome --python 3.13 && uv pip install --python .venv-esphome/bin/python esphome`
    (`uv` is pinned in `mise.toml`; `uvx esphome <cmd> firmware/tilehaus.yaml` also
    works for a one-off without the venv, but re-resolves per invocation)
  - compile: `.venv-esphome/bin/esphome compile firmware/tilehaus.yaml`
  - OTA:     `.venv-esphome/bin/esphome upload firmware/tilehaus.yaml --device <ip>`
  - logs:    `.venv-esphome/bin/esphome logs firmware/tilehaus.yaml --device <ip>`
- Run `npm run build` before compiling whenever `web/` changed — otherwise the
  device serves a stale configurator.

## The panel & its config API

The device serves the configurator at `/` (`/app.js`) and a config API at
`/api/v1/config`:

- `GET` → `200` with the binary DECK document (media type
  `application/vnd.tilehaus.deck`) plus `ETag`, `X-Display-Width`,
  `X-Display-Height`; or `204` when unconfigured.
- `PUT` (`Content-Type: application/vnd.tilehaus.deck` + `If-Match: "<gen>"`) →
  `204`, then the panel **reboots to apply**.
- `DELETE` (`If-Match`) → `204`, reboots to the awaiting-config screen.

Config is applied by **reboot** — there is no live in-place rebuild (HA state
subscriptions can't be torn down at runtime).

Default dev panel: `tilehaus.local` (Guition JC1060P470) — prefer the mDNS name,
the DHCP lease moves. OTA port 3232, no OTA
password.

> **Safety rule: after an OTA flash, do NOT push a config (PUT/DELETE) for >60s.**
> The P4 can roll back to safe mode if it reboots again too soon after an OTA.
> Wait until the panel is serving again (`panel-status`) before configuring.

## Interacting with the panel — skills

Prefer the skills in `.claude/skills/`: **flash**, **push-config**,
**panel-status**, **logs**, **reset**. They wrap the commands + `deck_cli.js` and
encode the safety rules above.

## Home Assistant — prefer the ha-mcp MCP server

When you need Home Assistant facts — entity IDs, current states, available
services, areas/floors — use the **ha-mcp** MCP tools (`mcp__ha-mcp__*`) instead of
guessing: e.g. `ha_get_overview`, `ha_search`, `ha_get_state`, `ha_get_entity`,
`ha_list_services`, `ha_call_service`. When building or validating a deck config
(a tile's `entity` / `entity2`), resolve and verify the entity IDs through ha-mcp
first so tiles bind to entities that actually exist. Follow the ha-mcp server's own
best-practices skill when it applies (e.g. entity_id over device_id, native helpers
over templates).

## Documentation (Zensical)

The public docs site is [Zensical](https://zensical.org) (Material for MkDocs team's
SSG; Markdown + `mkdocs.yml`). Content lives in `docs/` (the `docs_dir`); the nav is
in `mkdocs.yml`; the build output is `site/` (git-ignored). Internal planning docs
live in `planning/` — outside `docs_dir`, so they are not published.

Zensical installs in a Python venv (not pinned by mise):

```bash
python3 -m venv .venv && .venv/bin/pip install zensical
.venv/bin/zensical build      # or: npm run docs:build  (zensical on PATH)
.venv/bin/zensical serve      # or: npm run docs:serve   (live preview)
```

CI builds the site and deploys it to GitHub Pages on push to `main`
(`.github/workflows/docs.yml`). When you change firmware/web behaviour, update the
matching docs page (`docs/*.md`) in the same change.

## Workflow conventions

- Treat `main` as stable; branch for changes (short descriptive names).
- A compile/build pass is **not** user-confirmed device testing — distinguish the
  two, and name the panel when firmware needs flashing.
- **Commit messages: no Claude Code / co-author attributions, ever.** Files end with
  a trailing newline.
- The DECK format is versioned (`web/model/deck.ts` + `firmware/native/deck_document.h`,
  pinned by golden fixtures) — bump the version and update both sides + fixtures when
  changing the byte layout.
